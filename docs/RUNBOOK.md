# Operational Runbook — JHipster Sample Application

## 1. Service Overview

**Application**: JHipster Sample Application  
**Tech Stack**: Spring Boot 3, Angular, JPA (H2 in dev / PostgreSQL in prod), Liquibase  
**Domain Entities**: BankAccount, Operation, Label  
**Java Version**: 21  

The application is a full-stack web application generated by JHipster. It provides REST APIs for managing bank accounts, operations, and labels, with a modern Angular frontend.

## 5. Logging

### Format

- **Dev**: Console text format (default)
- **Prod**: Structured JSON via LogstashEncoder

### MDC Fields

Every log line in prod includes:

| Field           | Description                              |
|-----------------|------------------------------------------|
| `correlationId` | Request correlation ID (from `X-Correlation-ID` header or auto-generated UUID) |
| `userId`        | Authenticated user's login name          |
| `traceId`       | OpenTelemetry trace ID                   |
| `spanId`        | OpenTelemetry span ID                    |

### Querying Logs

To find all logs for a specific request:
```bash
# By correlation ID
jq 'select(.correlationId == "abc-123")' application.log

# By trace ID (correlate with distributed traces)
jq 'select(.traceId == "def-456")' application.log

# By user
jq 'select(.userId == "admin")' application.log
```

### Changing Log Levels at Runtime

```bash
# View current level
curl http://localhost:8080/management/loggers/io.github.jhipster.sample

# Set to DEBUG
curl -X POST http://localhost:8080/management/loggers/io.github.jhipster.sample \
  -H 'Content-Type: application/json' \
  -d '{"configuredLevel": "DEBUG"}'
```

## 6. Distributed Tracing

### Configuration

- **Dev**: 100% sampling rate
- **Prod**: 10% sampling rate (configurable via `management.tracing.sampling.probability`)
- **Propagation**: W3C Trace Context
- **Backend**: Grafana Tempo

### Finding Traces

1. Open Grafana at http://localhost:3000
2. Navigate to **Explore** → select **Tempo** datasource
3. Search by trace ID or use the service graph

### Correlating Logs with Traces

Every structured log entry contains `traceId` and `spanId`. Use these to find the corresponding trace in Tempo:

1. Find a log entry with an error
2. Copy the `traceId` value
3. Search for it in Tempo to see the full distributed trace

### Sampling Rate Configuration

```yaml
# application-prod.yml
management:
  tracing:
    sampling:
      probability: 0.1  # 10% — increase for debugging, decrease for high-traffic
```

## 8. Alerts

### Alert Rules

| Alert                    | Expression                                                                           | Duration | Severity | Meaning                                     |
|--------------------------|--------------------------------------------------------------------------------------|----------|----------|---------------------------------------------|
| HighErrorRate            | `rate(http_server_requests_seconds_count{status=~"5.."}[5m]) > 0.5`                 | 5m       | Critical | More than 0.5 server errors per second      |
| HighLatency              | `histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket[5m])) by (le)) > 2` | 5m       | Warning  | P95 latency exceeds 2 seconds               |
| JvmHeapPressure          | `jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"} > 0.85`     | 5m       | Warning  | Heap usage above 85%                        |
| HikariPoolExhaustion     | `hikaricp_connections_pending > 5`                                                   | 5m       | Critical | More than 5 threads waiting for connections |
| ApplicationDown          | `up == 0`                                                                            | 1m       | Critical | Application instance is unreachable         |
| HighInvalidTokenRate     | `rate(security_authentication_invalid_tokens_total[5m]) > 1`                         | 5m       | Warning  | Possible token-based attack                 |
| HighLoginFailureRate     | `failure / (success + failure) > 0.3`                                                | 10m      | Warning  | Login failure rate above 30%                |

### Notification Channels

Alertmanager is configured with two receivers:
- **default**: Catch-all receiver (configure webhook/email/slack)
- **critical**: High-priority receiver (configure PagerDuty/webhook)

Edit `src/main/docker/alertmanager/alertmanager.yml` to configure notification endpoints.

## 9. Common Failure Modes & Remediation

### High Error Rate (5xx)

**Symptoms**: `HighErrorRate` alert firing, spike in error rate dashboard  
**Investigation**:
1. Check application logs for stack traces: `jq 'select(.level == "ERROR")' application.log`
2. Check database connectivity: `curl localhost:8080/management/health/readiness`
3. Check HikariCP pool: look for connection exhaustion in Infrastructure dashboard  
**Remediation**: Fix application bugs, restart if OOM, scale database connections

### High Latency

**Symptoms**: `HighLatency` alert, P95 > 2s on Application Overview dashboard  
**Investigation**:
1. Check HikariCP pending connections for pool exhaustion
2. Check GC pause times for memory pressure
3. Look for slow queries via trace analysis in Tempo  
**Remediation**: Optimize queries, increase connection pool, tune GC, add caching

### JVM Heap Pressure

**Symptoms**: `JvmHeapPressure` alert, heap usage > 85%  
**Investigation**:
1. Check Infrastructure dashboard for heap trend
2. Look for memory leaks (steadily increasing heap)
3. Check GC pause frequency  
**Remediation**: Increase heap (`-Xmx`), investigate memory leaks with heap dump, optimize object creation

### Connection Pool Exhaustion

**Symptoms**: `HikariPoolExhaustion` alert, pending > 5  
**Investigation**:
1. Check for connection leaks (active connections at max with no pending resolution)
2. Check for long-running transactions
3. Verify database is responsive  
**Remediation**: Fix connection leaks, increase pool size (`spring.datasource.hikari.maximum-pool-size`), optimize transaction duration

### Application Down

**Symptoms**: `ApplicationDown` alert, `up == 0`  
**Investigation**:
1. Check container/pod status
2. Check resource limits (OOMKilled?)
3. Check application logs for fatal errors  
**Remediation**: Restart application, increase resource limits, fix root cause

### High Invalid Token Rate

**Symptoms**: `HighInvalidTokenRate` alert  
**Investigation**:
1. Check if JWT secret was recently rotated
2. Look for patterns in source IPs (possible attack)
3. Check token expiration settings  
**Remediation**: If attack, block source IPs; if secret rotation, wait for clients to re-authenticate; check for JWT secret compromise

## 10. Operational Procedures

### Starting the Application

```bash
# Development
./mvnw spring-boot:run

# With monitoring stack
docker compose -f src/main/docker/monitoring.yml up -d
./mvnw spring-boot:run
```

### Stopping the Application

```bash
# Graceful shutdown
kill -TERM <pid>

# Stop monitoring stack
docker compose -f src/main/docker/monitoring.yml down
```

### Rotating JWT Secrets

1. Generate a new Base64-encoded secret (min 512 bits for HS512)
2. Update `jhipster.security.authentication.jwt.base64-secret` in application config
3. Restart the application
4. Note: All existing tokens will be invalidated; users will need to re-authenticate

### Running Database Migrations

Liquibase migrations run automatically on startup. For manual control:

```bash
# Check migration status
./mvnw liquibase:status

# Run pending migrations
./mvnw liquibase:update

# Rollback last changeset
./mvnw liquibase:rollbackCount -Dliquibase.rollbackCount=1
```

### Scaling Horizontally

1. Ensure all instances share the same database
2. Use the same JWT secret across instances
3. Configure sticky sessions or stateless session management
4. Add instances to Prometheus scrape targets in `prometheus.yml`

### Enabling/Disabling Features via Spring Profiles

```bash
# Run with prod profile
./mvnw spring-boot:run -Dspring-boot.run.profiles=prod

# Run with multiple profiles
./mvnw spring-boot:run -Dspring-boot.run.profiles=prod,api-docs
```

3. Apply known remediation from this runbook

## 12. Disaster Recovery

### Database Backup

```bash
# PostgreSQL backup
pg_dump -h <host> -U <user> -d <database> -F c -f backup_$(date +%Y%m%d).dump

# Restore
pg_restore -h <host> -U <user> -d <database> backup_20260101.dump
```

### Cache Invalidation

The application uses Spring Cache with an in-memory provider:

```bash
# Clear all caches via actuator (if exposed)
curl -X DELETE http://localhost:8080/management/caches

# Or restart the application to clear all caches
```

### Rollback Procedures

1. **Application Rollback**: Deploy the previous version of the application
2. **Database Rollback**: Use Liquibase rollback (`./mvnw liquibase:rollbackCount`)
3. **Configuration Rollback**: Revert configuration changes and restart
4. **Full Rollback**: Restore database from backup + deploy previous application version

### Recovery Time Objectives

| Scenario              | RTO Target | RPO Target |
|-----------------------|------------|------------|
| Application restart   | 5 minutes  | 0          |
| Database failover     | 15 minutes | 1 minute   |
| Full disaster recovery| 1 hour     | 1 hour     |
